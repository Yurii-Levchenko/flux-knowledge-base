## Правила

1. **Кожен факт — з джерелом і датою.** Цифри AppKittie підписуємо «оцінка AppKittie».
2. **Факти окремо від припущень.** Припущення позначаємо **[гіпотеза]**.
3. **Мова — українська.** Назви компаній, інструментів і метрик — англійською.
4. **На початку документа:** автор, дата, статус (чернетка / готово).
5. **Зміни — лише через Pull Request.** Напряму змінювати `main` не можна, кожну зміну погоджує ще хтось із команди.

> ⚠️ **Репозиторій публічний — його бачить будь-хто.** Тут ніколи не має бути:
> - паролів, кодів доступу AppKittie, API-ключів;
> - особистих даних;
> - сирих вивантажень AppKittie та масивів відгуків (вони лежать локально в автора);
> - матеріалів лекцій школи.
>
> Якщо щось таке потрапило сюди випадково — одразу напиши Юрію.

## Як працювати з базою знань (для тих, хто не працював з GitHub)

### Словник

| Слово | Що означає |
|---|---|
| **Репозиторій (repo)** | Спільна папка з документами та повною історією змін |
| **main** | Головна «чиста» версія бази знань. Напряму її ніхто не змінює |
| **Гілка (branch)** | Твоя чернетка-копія, де ти робиш зміни |
| **Коміт (commit)** | Збережена зміна з коротким описом |
| **Pull Request (PR)** | Пропозиція влити твою чернетку в `main`. Тіммейт переглядає й погоджує |
| **Markdown (.md)** | Простий текстовий формат наших документів |

Робота завжди йде за одним циклом: **гілка → зміни → Pull Request → погодження тіммейтом → злиття в `main`**.

Зламати щось неможливо: GitHub зберігає кожну версію файлу.

### Крок 0. Один раз: акаунт і доступ

### Спосіб А (рекомендовано): прямо на сайті

Нічого не треба встановлювати. Працює однаково на Mac і Windows у будь-якому браузері.

**Змінити наявний документ:**
1. Відкрий потрібний файл у папці `docs` і натисни ✏️ **Edit this file**.
2. Внеси зміни. Вкладка **Preview** показує, як це виглядатиме.
3. Натисни **Commit changes…** і коротко опиши зміну, наприклад: «Додав ціни Ludex».
4. Обери **Create a new branch for this commit and start a pull request** → **Propose changes**.
5. Натисни **Create pull request**. Постав галочки в чек-листі опису.
6. Кинь посилання на PR у чат команди.

**Створити новий документ:**
1. Відкрий потрібну папку → **Add file → Create new file**.
2. Дай файлу назву латиницею з `.md` у кінці, наприклад `mvp_scope.md`.
3. Скопіюй структуру з [`templates/TEMPLATE.md`](templates/TEMPLATE.md).
4. Далі: **Commit changes… → new branch → Propose changes → Create pull request**.

**Додати файл (PDF, скриншот):** **Add file → Upload files**. Розмір — до 10 MB, і лише якщо файл справді потрібен.

### Перевірити чужу зміну (review)

1. Відкрий PR з чату або через вкладку **Pull requests**.
2. На вкладці **Files changed** зелене — додано, червоне — видалено.
3. Перевір:
   - чи є джерела й дати;
   - чи позначено `[гіпотеза]`;
   - чи немає секретів і сирих даних.
4. Натисни **Review changes** і обери:
   - **Approve** — якщо все добре;
   - **Request changes** — якщо треба доробити; додай коментар.
5. Після погодження автор натискає **Merge pull request → Confirm merge**.

Свій PR погодити сам не можна — потрібна інша людина.

### Шпаргалка Markdown

| Пишеш | Отримуєш |
|---|---|
| `# Заголовок`, `## Підзаголовок` | Заголовки |
| `- пункт` / `1. пункт` | Список / нумерований список |
| `**жирний**`, `*курсив*` | **жирний**, *курсив* |
| `[текст](https://посилання)` | Посилання |
| `\| A \| B \|` + рядок `\|---\|---\|` | Таблиця |

### Якщо щось пішло не так

| Ситуація | Що робити |
|---|---|
| «Protected branch» / «can't commit to main» | Так і має бути: створи нову гілку й PR |
| Немає ✏️ або «Permission denied» | Ти ще не прийняв запрошення або не надіслав нік Юрію |
| Конфлікт: двоє змінили той самий рядок | У PR натисни **Resolve conflicts** і залиш правильний варіант, або напиши в чат |
| Помилка вже потрапила в `main` | Створи новий PR з виправленням. Стара версія лишається в історії файлу (**History**) |

Питання — у чат команди.
